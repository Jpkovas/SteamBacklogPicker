## Threat Model

SteamBacklogPicker is a local desktop Steam-library picker with three materially different deployments: WPF on Windows, Avalonia on Linux sharing .NET AppCore/Domain/Infrastructure, and a separate SwiftUI/AppKit implementation on macOS. Windows and Linux combine installed manifests, local Steam profile/cache metadata and optional dynamically loaded Steam native APIs; macOS combines local files and automatically resolves missing names through the public Steam store API. Selection results can invoke numeric steam://run or steam://install URIs through the OS. Linux checks updates at startup; WPF registers a legacy Squirrel service but the inspected startup does not call it; macOS injects a no-op updater. Ordinary application operation uses the desktop user's authority, with no repository-established server, tenant boundary or separate Steam authentication system. ### Attacker Capabilities

- A remote metadata/image service or compromised permitted update endpoint can control the responses it serves, but does not thereby control local Steam files, configured public keys or the user's executable directory. A meaningful failure would have to cross parsing/rendering or update authenticity controls into new local authority.
- A local actor may control only files or directories permitted by the OS. Merely assuming control of this user's Steam DLLs, update marker, process environment or profile would often assume equivalent user authority; any privilege-gain claim must establish a narrower starting permission and a real new capability.
- A release/tool supplier can affect a fetched build tool or artifact; ordinary application users do not automatically possess GitHub release publishing rights or the signing private key. The privileged CI path must be assessed separately from desktop runtime.
- A custom caller of SteamHooks can select the documented prototype capability and targets within its existing process authority; there is no production wiring that turns every desktop start into memory inspection.

### Security Objectives

- Preserve executable authenticity from publisher/feed verification through staging and eventual replacement, and keep release credentials confined to their intended signing/publication consumers.
- Keep parser-derived game metadata and local profile identity from becoming arbitrary process commands; maintain numeric Steam URI construction and delegate actual game entitlements to Steam.
- Preserve user library, preferences and diagnostics privacy across local persistence, OS notifications and explicit network recipients; describe app-ID requests and path-bearing diagnostics accurately.
- Keep malformed or transient local Steam data and unavailable optional services from corrupting persistent selection state or preventing ordinary offline library use.
- Treat family-sharing labels as evidence-dependent metadata, and distinguish discovery completeness from Steam's authority to allow installation or execution.
- Keep experimental hooks separate from ordinary startup, with Linux process-memory probing subject to explicit configuration and OS read permissions.
